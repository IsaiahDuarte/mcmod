# Dedicated-server workload measurement — 2026-10-18

Partial A15/D07 evidence. This is the first in-world server measurement. It is not the full
release matrix: there are no clients, packets, crafting, Wasm guests or overload admission
scenario.

## Environment and reproduction

- **Hardware:** Apple M1 (MacBookPro17,1), 8 logical CPUs, 8 GiB RAM, macOS 15.3.1 arm64.
- **Software:** OpenJDK 21.0.12, Minecraft 1.21.1, NeoForge 21.1.252, dedicated server
  `--nogui`, `-Xmx2g`, flat world, simulation and view distance 2.
- **Loaded:** only Minecraft, NeoForge, Factory Core and the excluded verification
  fixture.
- **Revision:** built on `b33a211` with the benchmark harness committed alongside this
  record.
- **Command:** `./gradlew runBenchmarkServer` (manual; not part of `check`). Three
  separate runs. Other desktop processes and GC were not controlled, so outliers are
  retained.

`ServerBenchmark` places 64 factories, one per force-loaded chunk. Each has a controller,
a drive with a starter cell holding 4,096 cobblestone, a Program Controller kept topped up
with FE, and four Machine Interfaces labeled `bench` on chests. Labels are applied one
machine per network per tick, because settings are refused while that network rebuilds.

The phases run sequentially, with a 200-tick warmup and then 1,000 measured ticks each:

| Phase | Programs running | Of 64 factories |
| --- | --- | --- |
| Idle | none | all built |
| Small | 4 | the rest idle |
| Large | 64 | all |

The program keeps each machine at 64 and moves up to 16 back every 10 ticks, so items
churn continuously.

- **mod span:** time from a HIGHEST- to a LOWEST-priority `ServerTickEvent.Post`
  listener. This covers all of Factory Core's per-tick runtimes (networks/transfers,
  programs, crafting jobs).
- **server tick:** whole-tick time (Pre HIGHEST → Post LOWEST).

FE top-up happens in Pre and is outside the mod span. Block-entity tickers are outside the
mod span. After stopping all programs and waiting 200 ticks, total cobblestone (storage +
chests) must equal 262,144, and the large phase must leave items in machine chests;
otherwise the run fails.

[Raw gzip CSV](server-v1-2026-10-18.csv.gz) holds all 9,000 measured rows of the three
runs (gzip mtime 0). SHA-256:
`73495db2fe884871cf2bc4432f8464b25a158ce51912f43f0a39d9a9240ef067`.

## Observed (mod span, ms; three runs)

| Phase | Median | p95 | p99 | Max | Ticks > 2 ms | Ticks > 5 ms | Ticks > 10 ms | Items in machine chests |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Idle | 0.0086–0.0109 | 0.032–0.043 | 0.055–0.067 | 0.09–21.21 | 0–1 | 0–1 | 0–1 | 0 |
| Small | 0.42–0.47 | 1.19–1.35 | 1.31–1.47 | 3.59–17.29 | 1–2 | 0–1 | 0–1 | 960 |
| Large | 1.38–1.43 | 1.86–1.95 | 2.25–2.49 | 4.88–7.25 | 28–42 | 0–5 | 0 | 15,440–15,584 |

Whole-server-tick p99 was 0.34–0.42 ms idle, 1.48–1.63 ms small and 4.88–5.46 ms large.
Conservation held in all three runs (262,144 = 262,144). In the large phase, program moves
logged `technical_limit`: the scheduler refused admissions at its fixed shares, as
designed. That is backlog, not loss. JVM used heap after the run was 330–442 MiB for the
whole server; mod-owned memory was not isolated.

## Target assessment

Against ADR 0003, unchanged:
- **Met:**
  - small p99 ≤ 2 ms (1.31–1.47);
  - large p99 ≤ 5 ms (2.25–2.49);
  - p99 ≤ 10 ms in every phase;
  - conservation and bounded behavior under saturation.
- **Not universally met:**
  - 1–2 small ticks per 1,000 exceeded 2 ms, including one 17.3 ms tick;
  - 0–5 large ticks per 1,000 exceeded 5 ms;
  - one idle tick reached 21.2 ms in one run.

Single-tick outliers coincide with whole-server spikes of similar size, which suggests GC
or OS scheduling, but this is unverified. They are not relabeled as passes. Large-phase
admission refusals mean the configured 64×4 workload exceeds the per-tick shares, so
queue latency and throughput targets were not measured here.

**Not covered:** the overload scenario, 1,024-network idle, crafting/Wasm/JEI, network
packets and clients, multiplayer, Linux/Windows and memory isolation.
