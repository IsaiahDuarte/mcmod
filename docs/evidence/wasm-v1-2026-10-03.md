# Wasm feasibility measurements — version 1

This is a test-only interpreter probe, not a deployed scripting benchmark or
complete A09/A10/A15 evidence. D04's candidate is locally feasible under these
limits. No release performance target is declared passed by these measurements.

Environment: Apple M1, 8 GiB RAM, macOS 15.3.1 arm64, OpenJDK 21.0.12,
Chicory 1.7.5 interpreter, Rust 1.95.0, 2 GiB JVM maximum heap. The Java benchmark
uses the test classpath but does not start a Minecraft world. Baseline parent
revision: `2377399`; benchmark sources are included in this change. Background
desktop activity and JVM/GC variability were not controlled.

Command: `./gradlew spotlessApply build wasmBenchmark`. The final run passed
24 JVM tests, with no failures/skips, and produced 251 rows: the first startup,
then 250 measured samples after 20 warmup samples, in five passes of 50. Each
sample constructs an instance, makes 100 exact-quantity host round trips, then
constructs another instance and interrupts its infinite loop after 10,000
instructions. Loop timing excludes that second instance's startup. A preliminary
run lacking the first-startup row was exploratory and is not retained as evidence.

The 309-byte real Rust artifact SHA-256 is
`d89f72973971c2a13821829472aa309e4ff0da70857a76927d3d8b3b92206361`.
The [compressed raw CSV](wasm-v1-2026-10-03.csv.gz) contains nanoseconds and bytes.
Its SHA-256 is `e99a06f835cbfc9f18ff8c6d532b7ef139e281363c971af6aeb8e9cfb6b308f7`.
Percentiles use nearest-rank positions. Allocation values are the current
thread's allocated bytes; they are not retained-instance memory. Observed JVM
heap is neither a full mod-state bound nor a maximum-memory proof.

| Warm measurement | Median | p95 | p99 | Maximum |
| --- | --- | --- | --- | --- |
| Startup/parse/instantiate | 0.167917 ms | 0.543125 ms | 0.950000 ms | 2.001666 ms |
| 100 host echo callbacks | 0.090229 ms | 0.308042 ms | 0.596083 ms | 0.785916 ms |
| Interrupt 10,000 guest instructions | 0.295208 ms | 1.724167 ms | 2.016625 ms | 3.715250 ms |
| Startup allocation | 172,976 B | 172,976 B | 173,104 B | 175,112 B |
| 100 echo callback allocation | 101,600 B | 106,400 B | 106,400 B | 106,400 B |

The first instance took 107.716666 ms and allocated 11,630,480 B, including first
use/class initialization. Its 100 echoes took 7.423875 ms and loop interruption
took 7.240084 ms. Warm results do not justify synchronous cold initialization on
the server tick thread. P5 must bound and schedule admission/startup separately;
the artifact/type limits bound parser work, not a hard wall-clock preemption of
Java parsing or class loading. The tiny guest also does not represent a maximum
artifact; production admission measurements must include that workload.

Each fresh instance had two memory pages (131,072 B); the independent memory test
grew to 32 pages (2,097,152 B) and rejected further growth. Peak observed benchmark
heap was 84,383,216 B. P5 still owes aggregate instance quotas, persisted-state
ownership, real host-work costs, lifecycle/event/logging limits and scheduler
integration. Linux/Windows runtime/benchmark execution remains unverified.

Behavioral results: six WasmProbeTest tests passed, covering exact i64 beyond
2^53/Long.MAX_VALUE, negative inputs, finite instruction/deadline/host-call
budgets, memory growth, trap discard/non-resumption, parser declaration bombs,
unsupported imports/proposals, custom-section stripping, recursion and operand
stack accumulation across valid nested calls. These tests are required by `build`.
