# Dedicated-server workload, three quiet runs — 2026-10-19

This is the same `runBenchmarkServer` workload as
[2026-10-18](server-overload-v1-2026-10-18.md):
- idle;
- small and large (64 factories);
- overload (128 networks, each running an 8-rule program above the per-tick shares);
- drain and conservation;
- 1,024-network idle.

It ran on code that now includes throughput upgrades, preset continuations, program host limits
and the processing journal.

Environment: macOS 15.3.1 arm64 (Apple M1, 8 cores), Java 21.0.12, 2 GiB heap. No other build,
client or agent was running (`ps` showed no other JVM). There were three consecutive runs of
about 5m50s each. Raw per-tick CSVs and summaries: [run 1](server-v2-2026-10-19/run1-summary.txt),
[run 2](server-v2-2026-10-19/run2-summary.txt), [run 3](server-v2-2026-10-19/run3-summary.txt),
with `run*.csv.gz`.

Mod time per tick, in ms (p99 / max):

| Phase | Run 1 | Run 2 | Run 3 | ADR 0003 budget |
| --- | --- | --- | --- | --- |
| idle | 0.064 / 0.19 | 0.058 / 0.18 | 0.059 / 0.23 | — |
| small | 1.51 / 2.86 | **2.11** / 10.19 | 1.52 / 9.48 | p99 ≤ 2 |
| large | **8.28** / 36.32 | 2.67 / 8.99 | 2.91 / 6.02 | p99 ≤ 5 |
| overload | 3.38 / 5.45 | 3.19 / 7.53 | 3.06 / 4.77 | p99 ≤ 10 |
| 1,024-network idle | 0.058 / 0.17 | 0.048 / 0.46 | 0.062 / 0.18 | — |

Every run conserved exactly 524,288 items. The overload backlog stayed bounded (max about 1,120
of 8,192), and the 1,024-network idle queue was quiet.

The overload probe logs now show the A10 reporting. Rules that ran 20–23 ticks late logged
"ran N ticks late: server busy", and admission refusals logged `technical_limit` with
collapsed repeats.

## Assessment

These results are not universally met, so A15 stays partial.
- **Met:**
  - small p99 in 2 of 3 runs;
  - large p99 in 2 of 3 runs;
  - overload p99 in all runs;
  - conservation and boundedness in all runs.
- **Missed:**
  - **Run 1, large.** p99 was 8.28 ms, with 7 ticks over 10 ms and a 36 ms maximum.
  - **Run 2, small.** p99 was 2.11 ms, with one 10 ms tick.

The spikes coincide with whole-server tick spikes of similar size (run 1 large: server max
36.6 ms). That is consistent with GC or OS scheduling but not proven; no profiler was attached.
No budget was changed.

Still unmeasured:
